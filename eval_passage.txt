Transformer decoding is sequential: each token requires a full model forward pass. At small batch sizes this pass is memory-bound. That is, the bottleneck is loading the model's weights from GPU memory, not from computations like matrix multiplications. For a 7B-parameter model in float16, that's roughly 14 GB of weights loaded per token.
On a memory-bound device, processing multiple tokens in a single forward pass can cost almost the same as processing 1 token. The weights load once per pass regardless of sequence length (up to the point where sequence length itself becomes the bottleneck). So if you could produce multiple candidate tokens at a low cost and verify them all with 1 target model pass, you'd get multiple tokens for roughly the cost of 1.
The draft and target models must share the same vocabulary. The accept/reject step compares the draft model's probability q(xᵢ) and the target model's probability p(xᵢ) for the same token xᵢ. If the tokenizers differ then you would be comparing probabilities for completely different tokens. The code validates this at startup.
With the KV cache, the draft model generates each token from a single-token input, and the target model sees only the draft tokens during verification. The tricky part is cache synchronization. After verification, each model's cache covers the full sequence plus draft positions. We need to trim back to S + n (where n is the number of accepted tokens), then run one sync forward pass with the accepted "bonus" token. That sync step also captures each model's logit for the next round, which lets the next iteration start without an extra forward pass.
Both models process the full prompt once to build their KV caches. The KV cache stores computed attention keys and values for every prefix position, so future forward passes only need to process new tokens. Without the cache, every draft step and every verification pass would reprocess the entire growing prefix from scratch, which would negate the speedup entirely.
If the target assigns higher probability to xᵢ than the draft did, the ratio exceeds 1 and we always accept: there's no reason to reject a token the target likes even more than the draft did. If the target assigns lower probability, we accept with probability p/q, proportionally discarding the draft model's overconfidence rather than rejecting it outright, which keeps the output distribution unbiased instead of harsher.
There's one shortcut before the bonus-token step: if an accepted draft token is the EOS token, generation stops immediately and the bonus/residual sampling is skipped entirely. The paper's algorithm doesn't cover this case explicitly, since it assumes generation runs to a fixed length, but a real implementation has to check for it or risk sampling a bonus token past the end of a finished response.
The 75% vs 6.2% gap was not the models disagreeing, but rather it was 2 separate generation paths, one of which happened to have high model agreement and one that did not. To compare acceptance rates fairly across devices, average over multiple prompts and seeds rather than relying on a single run.
summary: "Choosing the best hardware for local LLMs requires evaluating trade-offs. Unified memory lets a Mac fit bigger models, but a comparable Windows/Linux machine with an NVIDIA GPU boasts better memory bandwidth, faster Time to First Token (TTFT), higher token throughput, and multi-user serving with CUDA ecosystem support."
I commonly read posts boasting how Apple's unified memory architecture allows developers to fit larger models and, therefore, a Mac is the obvious machine for serving local LLMs. I also read the mirrored version for NVIDIA threads: CUDA is faster and everything supports it so anything else is a toy. Both claims are true, but neither show the full picture.
A Mac buys you far more usable memory for a model on a fixed budget. A Mac mini with an M5 Pro chip and 48 GB of memory currently costs around $2,100, depending on storage, and can run a 70B model (around 35 GB using 4-bit quantization). A similarly priced PC with an NVIDIA GPU typically has 8 to 16 GB of VRAM, which cannot hold a 70B 4-bit model and its runtime buffers entirely in VRAM.
The difference is most noticeable as chat context grows or large documents are processed (e.g. "summarize this 40-page PDF"). For short prompts in a light single-user setup, decode throughput is often more noticeable than TTFT. In a shared server, queueing and batching can make TTFT important even for short prompts.
The CPU and GPU on Apple Silicon pull from the same memory controllers so if another process is heavily using memory (e.g. dozens of browser tabs) it competes with the GPU's model weight reads and token generation can slow down. The GPU has its own memory on a discrete card so whatever the CPU is doing is mostly irrelevant to inference, provided the entire model fits on the GPU.
The memory capacity a model receives on a Mac is not reserved. A browser with many tabs, Docker, or a virtual machine, for example, all shrink the pool the model can use. The model sits in its own dedicated memory on a PC with an NVIDIA GPU so a bloated browser costs next to nothing during inference.
Some tools arrived late to Apple's ecosystem. FlashAttention-style fused kernels now exist for Metal in llama.cpp and MLX, years after the CUDA original. Some tools solve a problem Mac does not have. vLLM's paged KV cache and most weight-offloading optimizations manage an NVIDIA GPU's fixed memory and the slow PCIe hop which unified memory sidesteps. Some tools lean on NVIDIA-specific hardware (tensor-core FP8 and FP4 math, warp-level primitives, NVLink) that Apple's GPU lacks or exposes differently so a port requires a complete rewrite.
These noise figures come from different labs, rigs, and workloads so take them with a grain of salt. The Mac mini is near-inaudible for light interactive use and audible only under sustained load while the RTX 5070 inside its host tower is audible whenever the GPU is working hard.
A desktop tower can generally sustain higher power and use much larger coolers than a Mac mini. That gives it more thermal headroom for long, heavy workloads, while the Mac mini prioritizes compactness, low power draw, and quiet operation at lighter loads.
A higher-memory Mac is compelling when you want a compact, low-power machine that can hold larger models without requiring a multi-GPU setup. An NVIDIA GPU is the stronger choice when you prioritize lower latency, more output tokens per second, mature CUDA tooling, high concurrency, or GPU-centric development.
